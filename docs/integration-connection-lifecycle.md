# Integration connection generation and refresh

This describes the EH02 credential generation and bounded HTTP publication contracts. Additive migration `036_integration_connection_revision.sql`, the complete matching API/main caller, and the reviewed EH03/EH09 transaction-capable authentication stores are required. Private automated qualification does not qualify live provider refresh, production migration, deployment, or the full enterprise program.

## Store contract

`IntegrationConnectionRecord.revision` is a required opaque UUID generated by PostgreSQL. The migration assigns distinct generations to existing rows without rewriting their encrypted credentials or metadata. Its trigger generates a fresh UUID on every insert/update, including legacy upserts, unchanged-value updates and caller-supplied revision values. Equality is the only supported operation; dates, timestamp precision, `xmin`, content hashes and ordering are not generation identities.

`getAccessToken(orgId, provider, expectedRevision?)` and `getRefreshToken(orgId, provider, expectedRevision?)` constrain SQL to that organization, provider and exact revision when supplied. A stale, disconnected, foreign or replaced generation yields no token. Existing administrative callers can omit the third argument; this compatibility path does not certify a captured operation's generation. Server-owned operations must always supply their admitted revision.

`saveRefreshedTokens(orgId, provider, expectedRevision, accessToken, {refreshToken?, expiresAt?})` returns `Promise<boolean>`. It performs one conditional UPDATE of an existing row, never an INSERT or upsert. Exactly one competing refresh can update the same captured generation. Missing/replaced/stale rows return false. The existing encryption owner encrypts tokens; omitted replacement refresh tokens preserve the exact existing ciphertext. Metadata, including encrypted bot tokens and future metadata fields, is untouched. Omitted expiry clears the prior expiry to unknown for the replacement token, matching previous refresh semantics; no fabricated expiry is inferred. Tokens are trimmed using the existing owner convention; blank tokens, embedded control/whitespace, tokens over 64 KiB UTF-8, invalid UUID/provider/expiry/options and missing encryption configuration fail before query dispatch with errors that contain no input values.

Both successful refreshes and legacy writes advance the revision. A successful conditional write is evidence that its captured generation won that database update, not a perpetual permission to use the returned vendor token. The `get()` record is server-internal metadata: do not serialize its raw encrypted bot metadata or tokens to clients. Existing public projections and source policy remain mandatory.

## Required caller and rollout integration

1. Capture the actual connection revision and read the refresh/access token using that exact revision. Preserve actor/org/provider/policy/source/ref admission and bounded cancellation owned by the actual API path.
2. For every provider refresh branch, replace refresh-time unconditional upsert with the conditional store method. On false, discard that returned vendor token; do not use it for subsequent retrieval or insert a replacement connection.
3. After successful refresh, the original revision is stale. Re-admit a current record and retrieve credentials with its exact revision before issuing content retrieval, carrying that record/revision through final authorization/publication. Never attach a reloaded newer revision to the old returned vendor token: disconnect/reconnect could have won between update and reload. A failed pinned read must deny/re-admit through the existing owner rather than fall back to an unpinned token.
4. Recheck the current actor, policy and carried connection revision on one transaction client while holding the real mutation rows through the synchronous response write. Sequential unlocked reads cannot provide this publication guarantee. Update complete matching types/test fixtures; do not make the required revision optional or substitute an arbitrary date/constant.
5. Apply the reviewed additive migration before deploying callers that select revision. Keep all historical SQL immutable. The volatile UUID default backfills existing rows and requires a table lock/rewrite; production size, lock budget, privileges and rollback/recovery must be qualified separately. Drain/update every old refresh executor before claiming the lifecycle repair: the database trigger alone cannot distinguish a legacy refresh upsert from a legitimate administrative reconnect, so an old unconditional INSERT can still recreate a row.

No SQL transaction is held across a vendor request. This CAS protects durable local credentials and supports final result fencing; it does not serialize external refresh-token exchanges. Two concurrent vendor exchanges may rotate/invalidate credentials externally even when only one local write wins. Provider-specific double-exchange/rotation, multi-instance coordination, already in-flight external work during disconnect, real vendor cancellation and bounded production SQL/auth waits remain open. Do not claim vendor exactly-once or successful provider concurrency from this local database test.

## Final HTTP publication barrier

Both `/v1/orgs/integrations/scope` and `/operate` use the existing API owner for final admission. The actual webhook factory supplies its database pool; missing durable admission capability fails closed. Vendor requests, credential refresh and final response serialization finish before the publication transaction. There is no callback-only or process-local production fallback.

The transaction locks the organization with `FOR UPDATE`, then the actor's user and exact session (or exact org API key), SAML configuration, sign-in policy, integration connection and source policy. The parent organization lock also conflicts with FK key-share checks when a missing child row is inserted; row locks on existing children conflict with their actual UPDATE/DELETE writers. This conservative order serializes final publication within an organization. Deadlock and fleet throughput qualification remain open; changing lock order or weakening these locks requires new mutation-order evidence.

Existing `OrgStore` and `UserStore`, and the connection/policy stores' `inTransaction(client)` bindings, perform canonical revalidation on the same client. Admission checks exact principal, role, session provider, current organization plan/suspension, connection generation/metadata and captured policy. Password/Google sessions also obey the locked sign-in policy. SAML session acceptance keeps the existing configuration fingerprint owner. The exact session expiry must be finite and is checked using current wall time after all lock waits, immediately before the synchronous response write.

The write under held locks is the publication point. A revocation or mutation acknowledged before admission wins and denies the captured response. A conflicting mutation started after admission waits for publication/release before it can acknowledge. Already queued response bytes cannot be recalled; this does not promise cancellation of external reads or delivery before a later revocation reaches the client.

Checkout and the complete final transaction have a 1500ms bound; SQL statements have a 1000ms server limit, row-lock waits 750ms, and idle transactions 1500ms. Initial transaction setup and rollback have client read bounds as well. Disconnect, cancellation or a final deadline destroys the owned transaction client; ordinary failure rolls back before returning a plain failure and releases the client. A late checkout after abandonment is released without running admission. No raw driver error or credential is returned. Failure after a synchronous admitted write cannot recall the response; no protected response is appended with another error body. These bounds qualify this publication phase, not all upstream authentication/retrieval waits.
